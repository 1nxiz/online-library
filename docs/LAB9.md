# Лабораторна робота №9. Балансування навантаження та доступність

**Мета:** розгорнути кілька екземплярів застосунку з ЛР-8 за єдиною точкою входу (nginx), дослідити розподіл запитів і поведінку системи при виході екземпляра з ладу та його відновленні, порівняти роботу з балансуванням і без нього.

## 1. Архітектура

```
                     http://localhost:8080  (єдина точка входу)
                                │
                         ┌──────▼──────┐
                         │    nginx    │  upstream library_app: round-robin,
                         │ 1.28-alpine │  max_fails=1 fail_timeout=10s,
                         └──┬───┬───┬──┘  proxy_next_upstream error/timeout/5xx
              ┌─────────────┘   │   └─────────────┐
       ┌──────▼─────┐    ┌──────▼─────┐    ┌──────▼─────┐
       │ app1 :8000 │    │ app2 :8000 │    │ app3 :8000 │   той самий handler.py,
       │ 172.30.0.11│    │ 172.30.0.12│    │ 172.30.0.13│   INSTANCE_ID = app1/2/3
       └──────┬─────┘    └──────┬─────┘    └──────┬─────┘
              └─────────────────┼─────────────────┘
                         ┌──────▼──────┐
                         │ LocalStack  │  DynamoDB "Books" (спільні дані)
                         └─────────────┘
   localhost:8001 → app1 напряму (для порівняння «без балансування»)
```

## 2. Що зроблено

| Файл | Призначення |
|---|---|
| `aws/app/server.py` | HTTP-сервер (стандартна бібліотека Python), що викликає `handler.handle()` з ЛР-8; заголовок `X-Instance`, JSON-логи; при старті створює таблицю, якщо її немає |
| `aws/app/Dockerfile` | образ `python:3.12-slim` + boto3; копіює `lambda/handler.py` і `server.py`; запуск не від root |
| `aws/nginx/nginx.conf` | upstream на 3 екземпляри, пасивна перевірка (`max_fails`, `fail_timeout`), повтор на наступний сервер (`proxy_next_upstream`), заголовок `X-Upstream`, журнал з адресою upstream |
| `aws/docker-compose.yml` | LocalStack + `app1`, `app2`, `app3` (healthcheck на `/health`, сталі IP) + `nginx` на порту 8080 |
| `aws/tests/test_server.py` | тести HTTP-сервера: `/health` з ідентифікатором, CRUD через HTTP, ідемпотентне створення таблиці |
| `scripts/lab9.ps1` | покроковий експеримент зі скріншотами і підсумковою таблицею (`aws/out/lab9-results.csv`) |

**Чому сталі IP.** nginx визначає адреси upstream один раз, при старті. Якщо зупинений `app2` після перезапуску отримав би нову IP-адресу, nginx його вже не знайшов би. Зі сталими адресами екземпляр повертається на ту саму адресу.

**Перевірка працездатності.** У nginx Open Source немає активних health-check, тому використано **пасивну** перевірку: після невдалої спроби з'єднання сервер вилучається з ротації на 10 с, а запит одразу повторюється на наступному сервері. Docker-healthcheck на `/health` показує стан кожного екземпляра в `docker compose ps`.

## 3. Запуск

```powershell
git checkout lab9
git pull
powershell -ExecutionPolicy Bypass -File scripts\lab9.ps1
```

Вручну:

```powershell
docker compose -f aws/docker-compose.yml up -d --build
1..9 | % { (Invoke-RestMethod http://localhost:8080/health).instance }   # app1 app2 app3 по черзі
docker compose -f aws/docker-compose.yml stop app2                     # вивести з роботи
docker compose -f aws/docker-compose.yml start app2                    # відновити
```

## 6. Висновок

Три екземпляри застосунку без стану, які працюють зі спільною DynamoDB, обслуговуються через єдину точку входу nginx. Round-robin розподіляє запити рівномірно. Коли один екземпляр виходить з ладу, nginx перенаправляє запити на інші без помилок для клієнта, а після відновлення автоматично повертає екземпляр у ротацію. Без балансувальника відмова єдиного екземпляра означає повну недоступність сервісу.
